# 模型切换与动态调度

本文档涵盖 LLM 推理系统中的高级模型切换技术，包括 token 级调度、动态模型切换和快速模型驱动。这些技术在生产环境中实现高效的多模型服务、减少延迟和优化资源利用率。

## 概述

模型切换是现代 LLM 推理系统中的关键操作，可以实现：

- **在有限的 GPU 资源上进行多模型服务**
- **基于请求模式的动态资源分配**
- **通过高效 GPU 利用实现成本优化**
- **多租户推理平台的延迟降低**

传统模型切换需要：

- 重启 Python 进程
- 重新初始化 CUDA 上下文
- 重新编译 GPU 内核
- 重新捕获 CUDA 图

这导致每次模型切换的开销为 30-100 秒，使得频繁模型切换不切实际。

**现代方法**通过以下方式优化模型切换：

1. **Token 级调度**——在每个 token 之后做出切换决策
2. **休眠模式**——在释放 GPU 内存的同时保留进程状态
3. **组件复用**——共享已编译的内核和 CUDA 图
4. **KV 缓存同步**——高效传输缓存数据

这些技术将模型切换开销减少**高达 97%**，实现亚秒级切换延迟的实时多模型服务。

## 阿里 Aegaeon：Token 级调度

[Aegaeon](https://mp.weixin.qq.com/s/uJyk0HALKFZysTAgghjgpw) 是阿里巴巴的分布式 LLM 服务系统，开创了 **token 级调度**，使系统能够在每个生成的 token 之后做出动态模型切换决策。

### 关键创新：Token 级调度

传统推理系统在请求级别做出模型选择决策。Aegaeon 引入了 **token 级粒度**，使系统能够：

- 在每个 token 生成后评估模型切换需求
- 基于延迟要求在推理中间切换模型
- 同时服务多个模型同时满足 SLO
- 实时优化资源分配

### 架构和组件

Aegaeon 实现为分布式 LLM 服务系统，包含：

- **5,700 行** Python 和 CUDA/C++ 代码
- **控制面**：基于 asyncio 实现并发编排
- **数据面**：使用 Ray 进行分布式数据管理
- **执行后端**：利用 vLLM 实现广泛的架构支持

![Aegaeon 实现架构](https://github.com/user-attachments/assets/e3aea800-f62d-465a-b6f7-92753500f445)

*图 1：Aegaeon 实现——控制面使用 asyncio 实现并发，数据面使用 Ray 进行分布式管理，vLLM 提供模型执行后端，支持 FlashAttention 和 PagedAttention 等现代优化。*

### 核心能力

#### 1. 精确执行时间预测

Aegaeon 使用机器学习模型预测：

- 每个模型的 token 生成延迟
- 每个请求的资源需求
- 推理期间的最佳切换点

#### 2. Token 级调度算法

调度器基于以下因素确定模型切换：

- 请求剩余的**当前延迟预算**
- 候选模型的**预测执行时间**
- 跨集群的**资源可用性**
- 请求的 **SLO 要求**

#### 3. 模型切换优化

Aegaeon 通过以下方式将切换开销减少 **97%**：

**组件复用：**

- 跨切换保留已编译的 CUDA 内核
- 兼容模型之间复用 CUDA 图
- 共享内存分配器和 GPU 上下文

**细粒度 GPU 内存管理：**

- 切换期间仅释放必要内存
- 维护内核编译缓存
- 保留已初始化的 CUDA 上下文

**优化的 KV 缓存同步：**

- 模型间高效传输 KV 缓存
- 切换期间最小化数据复制
- 选择性缓存保留

### 性能特征

- **切换延迟**：亚秒级（从 30-100 秒减少）
- **开销减少**：相比传统方法高达 97%
- **并发模型**：同一 GPU 资源上的多个模型
- **SLO 合规**：通过动态调度满足延迟要求

### 用例

Aegaeon 特别适用于：

- **质量-延迟权衡**：在延迟压力下切换到更快的模型
- **多租户服务**：为不同用户提供不同模型大小
- **成本优化**：在质量要求允许时使用较小的模型
- **混合服务**：结合大模型和小模型实现最优成本/质量

## vLLM 休眠模式：快速模型切换

[vLLM 休眠模式](https://blog.vllm.ai/2025/10/26/sleep-mode.html)（2025 年 10 月发布）通过在释放 GPU 内存的同时保留进程状态，实现超快速模型切换。

### 挑战

多模型服务传统上面临痛苦的困境：

- **同时加载**：GPU 内存爆炸 💸
- **频繁切换**：30-100 秒等待时间 🐌

### 休眠模式解决方案

vLLM 休眠模式提供两个操作级别：

#### 级别 1：CPU 内存卸载

**特征：**

- 模型权重移至 CPU RAM
- CUDA 上下文和已编译内核保留
- 唤醒时间：**0.1-0.8 秒**
- 适用于内存充足的环境

**内存要求：**

- GPU 内存：已释放（模型已卸载）
- CPU 内存：完整模型权重保留
- 进程状态：完全保留

#### 级别 2：完全丢弃权重

**特征：**

- 模型权重完全丢弃
- 仅保留进程状态
- 内存占用：**仅 MB 级别**
- 适用于成本敏感型部署

**内存要求：**

- GPU 内存：已释放
- CPU 内存：最小（仅进程状态）
- 重新加载需要：从存储完全重新加载模型

### 休眠模式为何快速

传统模型切换需要：

❌ 重启 Python 进程
❌ 重新初始化 CUDA 上下文
❌ 重新编译 GPU 内核
❌ 重新捕获 CUDA 图

休眠模式保留进程状态：

✅ 保留内存分配器
✅ 保留 CUDA 图
✅ 缓存 JIT 编译的内核
✅ 保持完整进程状态

### 性能基准

#### A100 大型模型测试

**Qwen3-235B（TP=4）：**

- 冷启动：97.7 秒 😫
- 休眠唤醒：5.4 秒 ⚡
- **加速：18 倍**

**Qwen3-Coder-30B：**

- 冷启动：47.4 秒 😫
- 休眠唤醒：2.9 秒 ⚡
- **加速：17 倍**

#### A4000 小型模型测试

**Qwen3-0.6B + Phi-3-vision：**

- 唤醒时间：0.1-0.8 秒
- 相当于响指 🫰
- **加速：58-203 倍**

#### 多切换场景

**5 次模型切换对比：**

- 传统：357 秒
- 休眠模式：125 秒
- **节省时间：65%（232 秒）**

### 首次推理优化

休眠模式还加速了初始推理：

- **首 token 延迟**：快 61-88%
- 得益于保留的 CUDA 图
- 无内核重新编译开销

### 配置和使用

```python
# vLLM 休眠模式配置
from vllm import EngineArgs

engine_args = EngineArgs(
    model="Qwen/Qwen3-Coder-30B",
    sleep_mode="level1",  # 或 "level2"
    sleep_timeout=300,    # 空闲 5 分钟后休眠
    preserve_kv_cache=True
)
```

**级别选择指南：**

- **级别 1**：当您有足够的 CPU RAM 且需要最快唤醒速度时
- **级别 2**：当内存成本至关重要且您可以容忍轻微延迟时

### 理想用例

✅ **多模型服务**（客服 + 翻译 + 代码助手）
✅ **开发/测试**（频繁模型切换）
✅ **成本优化**（小型 GPU 实例）
✅ **云部署**（按用量付费）

## 模型切换方法对比

| 特性 | 传统 | Aegaeon | vLLM 休眠模式 |
|-----------------------|-------------|-------------|---------------------|
| **切换延迟** | 30-100s | <1s | 0.1-5.4s |
| **开销减少** | 基准 | 97% | 18-203 倍加速 |
| **粒度** | 请求级 | Token 级 | 进程级 |
| **GPU 内存** | 完全释放 | 优化 | 完全释放 |
| **状态保留** | 无 | 选择性 | 完整进程状态 |
| **CUDA 图复用** | 否 | 是 | 是 |
| **内核缓存** | 否 | 是 | 是 |
| **KV 缓存处理** | 丢弃 | 同步 | 可选保留 |
| **最适合** | 单模型 | 动态 QoS | 多模型开发/测试 |

### 何时使用每种方法

**使用传统切换：**

- 运行单模型工作负载
- 模型变更不频繁（相隔数小时/天）
- 内存不受限

**使用 Aegaeon Token 级调度：**

- 需要在推理期间进行质量-延迟权衡
- 服务具有不同 SLO 的多样化请求模式
- 在保持质量阈值的同时优化成本
- 运行生产多模型服务

**使用 vLLM 休眠模式：**

- 在相同硬件上支持多个模型
- 开发和测试环境
- 成本敏感的云部署
- 模型具有可预测的空闲期

## 生产用例

### 多租户 AI 平台

**场景**：为用户提供不同模型大小的 SaaS 平台

**解决方案**：结合 Aegaeon + 休眠模式

- 使用 Aegaeon 进行实时质量-延迟优化
- 使用休眠模式最大化 GPU 利用率
- 在相同硬件上支持 5-10 倍更多的模型
- 保持 SLO 同时降低成本

### 开发环境

**场景**：ML 工程师测试多个模型变体

**解决方案**：vLLM 休眠模式级别 1

- 在 CPU 内存中保留模型以便即时访问
- 在 0.1-0.8 秒之间切换模型
- 空闲模型不浪费 GPU 内存
- 保留 KV 缓存用于测试迭代

### 成本优化生产

**场景**：预算有限的初创公司

**解决方案**：vLLM 休眠模式级别 2

- 每个模型最小内存占用
- 在单个 GPU 上服务 10+ 个模型
- 接受 2-5 秒唤醒延迟
- 针对成本而非绝对性能进行优化

### 混合质量服务

**场景**：具有不同质量要求的应用

**解决方案**：Aegaeon Token 级调度

- 从复杂请求的大型模型开始
- 在延迟压力下切换到较小的模型
- 在 SLO 内保持可接受的质量
- 降低服务成本 30-50%

## 最佳实践

### 架构设计

1. **选择合适的粒度**
   - Token 级用于动态优化
   - 请求级用于简单实现
   - 进程级用于资源效率

2. **规划内存层次**
   - GPU 内存：热模型
   - CPU 内存：温模型（休眠模式级别 1）
   - 磁盘/存储：冷模型（休眠模式级别 2）

3. **实现智能路由**
   - 将请求路由到适当的模型
   - 考虑模型亲和性以实现 KV 缓存复用
   - 在可用实例之间平衡负载

### 性能优化

1. **监控切换指标**
   - 跟踪切换频率
   - 测量唤醒延迟（P50、P95、P99）
   - 监控 GPU 内存利用率

2. **调整休眠超时**
   - 平衡延迟与资源利用率
   - 对不同模型层级使用不同的超时
   - 在超时选择中考虑使用模式

3. **优化 KV 缓存处理**
   - 为长对话保留缓存
   - 实现缓存驱逐策略
   - 考虑存储的缓存压缩

### 可靠性

1. **优雅处理故障**
   - 为失败的唤醒实现回退
   - 监控唤醒成功率
   - 规划优雅降级

2. **保持服务质量**
   - 设置适当的 SLO 阈值
   - 监控切换后的质量指标
   - 对过度切换延迟发出告警

3. **测试切换场景**
   - 在负载下验证切换
   - 测试边缘情况（快速切换、并发唤醒）
   - 验证切换后的 KV 缓存正确性
