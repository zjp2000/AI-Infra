## 架构概述

现代 LLM 架构大致可分为两大类：

**密集模型：** 传统 transformer 架构，每个 token 激活所有参数。这些模型提供可预测的性能和更简单的部署，但随参数数量线性扩展。

**混合专家（MoE）模型：** 高级架构，仅激活每个 token 的一小部分专门的"专家"网络。MoE 模型实现了卓越的参数效率，可以扩展到更大的总参数量，同时保持快速的推理速度。

---

## 密集模型

密集模型对每个输入 token 激活所有参数，提供一致且可预测的行为。它们易于理解，得到推理引擎的广泛支持，并在其参数规模上提供出色的质量。

### Llama 3

[`Llama 3`](https://github.com/meta-llama/llama3) 是 Meta 的第三代密集 transformer 架构，代表了开源密集模型的最先进性能。

**架构特征：**

- **模型类型：** 密集 transformer（decoder-only）
- **可用规模：** 8B、70B 和 405B 参数
- **上下文长度：** 最高 128K tokens（扩展上下文版本）
- **训练数据：** 跨多个领域的 15+ 万亿 tokens
- **分词器：** 增强的分词器，128K 词汇量
- **架构特性：**
  - 分组查询注意力（GQA）实现高效推理
  - RoPE（旋转位置嵌入）用于位置编码
  - 前馈层中的 SwiGLU 激活函数
  - 使用 RMSNorm 进行预归一化

**关键规格（Llama 3.1）：**

| 模型 | 参数 | 隐藏层大小 | 层数 | 注意力头数 | KV 头数 |
|-------|-----------|-------------|--------|-----------------|----------|
| Llama 3.1 8B | 8B | 4096 | 32 | 32 | 8 |
| Llama 3.1 70B | 70B | 8192 | 80 | 64 | 8 |
| Llama 3.1 405B | 405B | 16384 | 126 | 128 | 8 |

**优势：**

- **质量：** 开源密集模型中的领先性能
- **效率：** GQA 减少 KV 缓存大小并提高吞吐量
- **长上下文：** 原生支持扩展上下文长度
- **生态系统：** 广泛的工具和推理引擎支持

**推理考虑因素：**

- 在单 GPU 或多 GPU 设置上直接部署
- 所有主要推理引擎（vLLM、SGLang、TensorRT-LLM）均提供良好支持
- 内存需求随模型大小线性扩展
- 适用于需要一致延迟的应用程序

**用例：**

- 通用聊天和助手应用
- 高质量内容生成
- 代码生成和分析
- 长文档理解和摘要

## 混合专家（MoE）模型

MoE 模型通过引入稀疏激活的专家网络革新了 LLM 架构。MoE 模型不是通过所有参数处理每个 token，而是将 token 路由到一小部分专门的专家，大幅提高参数效率和推理速度。

**核心 MoE 原理：**

1. **稀疏激活：** 只有一小部分模型参数对每个 token 处于活跃状态（通常为 10-20% 的专家）
2. **专家专业化：** 不同的专家学会处理不同类型的输入（语言、领域、任务类型）
3. **动态路由：** 门控网络学会为每个输入 token 选择最相关的专家
4. **参数效率：** 使用更少的每 token 活跃参数，实现与更大的密集模型相当的质量

有关 MoE 架构的详细信息，请参见 [大规模专家模型（MoE 模型）](./large-scale-experts.md)。

### Llama 4

**注意：** Llama 4 预计发布但尚未发布。此处所有规格均为假设性，基于预期的 MoE 从 Llama 3 演进的架构趋势。这些细节应在模型发布后与官方文档进行核实。

Llama 4 预计代表 Meta 向混合专家架构的演进，将 Llama 3 的架构进步与稀疏专家激活相结合，以提高效率和规模。

**架构特征：**

- **模型类型：** MoE transformer（decoder-only）
- **专家配置：** 多个专门的专家网络
- **路由策略：** 每个 token 的 Top-K 专家选择
- **总参数：** 显著大于 Llama 3，但每个 token 的活跃参数相当
- **核心特性：**
  - 继承 Llama 3 架构的 GQA
  - RoPE 位置嵌入
  - 专家网络中的 SwiGLU 激活
  - 用于专家利用率的负载均衡路由

**MoE 设计：**

```text
输入 Token
    ↓
共享自注意力层（密集）
    ↓
路由器网络
    ↓
Top-K 专家选择
    ↓
[专家 1] [专家 2] ... [专家 N]（仅 top-K 激活）
    ↓
加权专家输出聚合
    ↓
输出
```

**相对于密集 Llama 3 的优势：**

- **推理速度：** 相同质量水平下快 2-3 倍
- **内存效率：** 每个 token 活跃参数更少
- **可扩展性：** 可扩展到更大的总参数量
- **专业化：** 专家可以为不同领域/语言进行专业化

**推理考虑因素：**

- 需要专家感知的推理引擎（vLLM、SGLang、TensorRT-LLM）
- 专家路由的全对全通信模式
- 多 GPU 部署需要专家并行
- 跨专家的动态负载均衡

**用例：**

- 高吞吐量服务应用
- 多领域和多语言应用
- 追求最大效率的成本敏感型部署
- 推理速度至关重要的应用

### Qwen 3

[`Qwen 3`](https://github.com/QwenLM/Qwen)（Qwen2.5 系列）来自阿里云，实现了灵活的混合架构，支持密集和 MoE 配置，为不同用例提供部署灵活性。

**架构特征：**

- **模型类型：** 混合——同时提供密集和 MoE 变体
- **可用配置：**
  - **密集模型：** 0.5B、1.5B、3B、7B、14B、32B、72B 参数
  - **MoE 模型：** Qwen2.5-MoE，具有多种专家配置
- **上下文长度：** 最高 32K tokens（某些变体可达 128K）
- **多语言：** 对英语和中文的强力支持
- **训练：** 在代码、数学和多语言数据上进行广泛训练

**MoE 配置（Qwen2.5-MoE）：**

| 模型 | 总参数 | 活跃参数 | 专家数 | 每 Token 专家数 |
|-------|-------------|---------------|---------|---------------|
| Qwen2.5-MoE-A2.7B | ~14B | 2.7B | 60 | 8 |
| Qwen2.5-MoE-A14B | ~65B | 14B | 64 | 8 |

**独特特性：**

- **混合方法：** 密集和 MoE 变体具有一致的 API
- **细粒度专家：** 大量较小专家实现更好的专业化
- **代码优化：** 针对编程任务的专业化专家
- **多专家路由：** 将每个 token 路由到多个（8 个）专家以获得更好质量

**架构亮点：**

- 分组查询注意力（GQA）实现高效 KV 缓存
- 支持扩展上下文的 RoPE
- 支持多语言的增强分词器
- 带有辅助损失的负载均衡专家路由

**优势：**

- **灵活性：** 根据部署需求在密集和 MoE 之间选择
- **质量：** 在中文和代码基准测试中的领先性能
- **效率：** MoE 变体提供卓越的质量成本比
- **部署：** 在密集和 MoE 版本之间平滑迁移

**推理考虑因素：**

- 密集模型：标准部署模式
- MoE 模型：需要具有 60+ 个专家的专家并行
- 考虑对常用专家进行专家缓存策略
- 由于专家数量多，负载均衡至关重要

**用例：**

- **密集变体：** 单 GPU 部署、延迟关键型应用
- **MoE 变体：** 高吞吐量服务、多语言应用
- 不同端点的混合部署
- 代码生成和分析任务

### DeepSeek-V3

[`DeepSeek-V3`](https://github.com/deepseek-ai/DeepSeek-V3) 代表了大规模 MoE 架构的最先进水平，通过 256 个专家和先进的路由机制推动高效扩展的边界。

**架构特征：**

- **模型类型：** 大规模 MoE transformer（decoder-only）
- **总参数：** 总 671B，每 token 活跃 37B
- **专家配置：** 256 个专家，支持多 token 预测
- **上下文长度：** 最高 128K tokens
- **训练：** 具有专家专业化的多阶段训练
- **路由策略：** 带有辅助损失的高级负载均衡路由

**高级 MoE 特性：**

- **多 Token 预测：** 专家可以预测多个未来 token
- **分层专家组织：** 按专业化分组专家
- **动态专家容量：** 每个专家的自适应容量分配
- **细粒度负载均衡：** 防止专家崩溃的复杂路由算法

**架构规格：**

```text
总参数：671B
每 Token 活跃参数：37B（约 5.5% 激活率）
专家数量：256
每 Token 激活专家数：可变（通常 6-8）
专家规模：每个约 2.6B 参数
隐藏维度：7168
层数：61
注意力头数：128（16 KV 头，使用 GQA）
```

**关键创新：**

1. **大规模专家并行：**
   - 256 个专家实现前所未有的专业化
   - 跨 GPU 的分层专家分布
   - 优化的全对全通信模式

2. **多 Token 预测：**
   - 专家可以同时预测多个未来 token
   - 提高自回归生成的吞吐量
   - 减少解码中的顺序依赖

3. **专家专业化：**
   - 领域特定专家（数学、代码、推理）
   - 支持多语言的语言特定专家
   - 任务类型专家（问答、生成、分析）

4. **负载均衡：**
   - 鼓励均衡专家使用的辅助损失函数
   - 动态容量分配防止专家过载
   - 推理期间的监控和调整

**性能特征：**

| 指标 | DeepSeek-V3 | GPT-4 | 说明 |
|--------|------------|-------|-------|
| 活跃参数 | 37B | ~1.7T（估计） | 活跃参数减少约 46 倍 |
| 推理速度 | 快 3 倍 | 基准 | 相同质量水平 |
| 每 Token 内存 | 低 65% | 基准 | 由于稀疏激活 |
| 训练效率 | 快 4 倍 | 密集等效 | 每训练 FLOP |

**优势：**

- **极致效率：** 巨大的总容量，最小的活跃计算
- **质量：** GPT-4 级别的性能，活跃参数成本仅为其一小部分
- **专业化：** 256 个专家实现细粒度的领域专业知识
- **可扩展性：** 已验证的可扩展到万亿以上参数的架构
- **性价比：** 相比密集等效模型，服务成本显著降低

**推理考虑因素：**

- 需要 32+ 个 GPU 才能高效部署
- 专家并行是必需的（分布 256 个专家）
- 高带宽互连至关重要（NVLink、InfiniBand）
- 需要复杂的负载均衡和监控
- 考虑对频繁激活的专家进行专家缓存

**部署模式：**

```yaml
# 示例：DeepSeek-V3 多节点部署
# 概念性配置
apiVersion: v1
kind: Service
metadata:
  name: deepseek-v3
spec:
  replicas: 8  # 数据并行：8 副本
  template:
    spec:
      containers:
      - name: vllm
        args:
        # 每个副本使用 32 个 GPU 进行专家并行
        - --tensor-parallel-size=2  # 共享层
        - --expert-parallel-size=16  # 256/16 = 每 GPU 16 个专家
        resources:
          limits:
            nvidia.com/gpu: "32"
```

**用例：**

- **企业 LLM 服务：** 需要 GPT-4 质量但成本更低的企业
- **多领域应用：** 处理多种查询类型的系统
- **高吞吐量推理：** 每秒服务数千个请求
- **研究平台：** 探索大规模 MoE 架构
- **多语言服务：** 需要多种语言的全球应用

**挑战：**

- 需要大量基础设施的复杂部署
- 需要专家感知的编排和监控
- 负载均衡和专家利用率优化
- 相比密集模型，设置复杂度更高

## 扩散模型

虽然基于 transformer 的 LLM 主导文本生成，但扩散模型已成为图像生成和其他模态的最先进技术。

### Flux

[`Flux`](https://github.com/black-forest-labs/flux) 是由 Black Forest Labs 开发的最先进的文本到图像扩散模型，代表了图像生成质量和效率的最新进展。

**架构特征：**

- **模型类型：** 潜在扩散 transformer
- **可用变体：**
  - **Flux.1 [pro]：** 最高质量，仅 API
  - **Flux.1 [dev]：** 开放权重，非商业许可
  - **Flux.1 [schnell]：** 快速变体，Apache 2.0 许可
- **总参数：** 12B 参数
- **架构：** 具有并行注意力路径的流匹配 transformer

**关键特性：**

- **混合架构：** 结合扩散过程与 transformer 层
- **流匹配：** 提高质量的高级训练技术
- **并行注意力：** 分离的文本和图像注意力路径
- **引导蒸馏：** 在 schnell 变体中无需 CFG（无分类器引导）即可实现高质量生成

**架构组件：**

```text
文本输入
    ↓
文本编码器（T5 或 CLIP）
    ↓
[具有并行注意力的 Transformer 块]
    ├─ 文本注意力路径
    └─ 图像潜在注意力路径
    ↓
流匹配扩散过程
    ↓
VAE 解码器
    ↓
生成图像
```

**各变体规格：**

| 变体 | 步数 | 速度 | 质量 | 许可 |
|---------|-------|-------|---------|---------|
| Flux.1 [pro] | 50 | 较慢 | 最高 | 专有（API） |
| Flux.1 [dev] | 50 | 中等 | 高 | 非商业 |
| Flux.1 [schnell] | 4 | 快速 | 良好 | Apache 2.0 |

**优势：**

- **质量：** 最先进的图像生成质量
- **提示遵循：** 对复杂提示的出色理解
- **效率：** Schnell 变体仅需 4 步生成（而 SD 需 50+ 步）
- **开放权重：** Dev 和 schnell 变体可用于部署
- **灵活性：** 多个变体满足不同的速度/质量权衡

**推理考虑因素：**

- 需要大量 GPU 内存（12B 参数 + VAE）
- 批处理多个请求可提高吞吐量
- Schnell 变体适合实时应用
- 可与 LoRA 结合实现微调风格
- 支持各种纵横比和分辨率

**部署模式：**

```python
# 示例：使用 Diffusers 库进行 Flux 推理
from diffusers import FluxPipeline

pipe = FluxPipeline.from_pretrained(
    "black-forest-labs/FLUX.1-schnell",
    torch_dtype=torch.bfloat16
)
pipe.to("cuda")

# 快速生成（4 步）
image = pipe(
    prompt="A serene landscape with mountains",
    num_inference_steps=4,
    guidance_scale=0.0  # 引导已蒸馏，不需要
).images[0]
```

**用例：**

- **创意工具：** AI 艺术生成、设计辅助
- **营销：** 产品可视化、广告创意生成
- **游戏：** 资产生成、概念艺术
- **电商：** 产品图像生成和变体
- **实时应用：** 实时图像生成（使用 schnell 变体）

**与 LLM 基础设施的集成：**

Flux 模型可以与 LLM 推理基础设施一起部署：

- 多模态应用的共享 GPU 池
- 结合 LLM 提示增强的文本到图像流水线
- 用于文本和图像生成的统一 API 网关
- 同时考虑 LLM 和扩散工作负载的资源调度

## 架构对比

理解不同架构之间的权衡有助于为您的用例选择正确的模型。

### 密集 vs. MoE 对比

| 方面 | 密集（Llama 3） | MoE（DeepSeek-V3、Llama 4） |
|--------|----------------|---------------------------|
| **活跃参数** | 所有参数 | 总参数的 5-20% |
| **推理速度** | 基准 | 快 2-3 倍（相同质量） |
| **每 Token 内存** | 100% | 35-40% |
| **部署复杂度** | 简单 | 中到高 |
| **延迟可预测性** | 一致 | 可变（路由开销） |
| **多领域质量** | 良好 | 优秀（专业化） |
| **吞吐量扩展** | 随 GPU 线性增长 | 超线性（专家并行） |
| **每 Token 成本** | 基准 | 低 40-60% |

### 模型选择指南

#### 选择密集模型的场景

- **简单部署：** 单 GPU 或简单的多 GPU 设置
- **一致延迟：** 可预测的性能至关重要
- **小规模：** 有限的请求量
- **单一领域：** 专注的应用领域
- **调试：** 更易于理解和排查问题

**推荐：** Llama 3（8B、70B）

#### 选择 MoE 模型的场景

- **高吞吐量：** 每秒服务数千个请求
- **多领域：** 处理多种查询类型
- **成本效率：** 优化服务成本是优先任务
- **大规模：** 具有多 GPU 集群的大规模部署
- **质量优先：** 每个活跃参数需要最大质量

**推荐：**

- **中等规模：** Llama 4、Qwen2.5-MoE-A2.7B
- **大规模：** DeepSeek-V3、Qwen2.5-MoE-A14B

#### 选择混合方法的场景

- **灵活部署：** 不同端点的不同需求
- **迁移路径：** 从密集到 MoE 的逐步过渡
- **混合工作负载：** 结合延迟关键型和批处理工作负载

**推荐：** Qwen 3（密集和 MoE 变体均可选）

### 性能对比

基于公开基准测试和生产部署：

| 模型 | 类型 | 活跃参数 | 吞吐量（相对） | 延迟（TTFT） |
|-------|------|--------------|---------------------|---------------|
| Llama 3 8B | 密集 | 8B | 1.0x | 50ms |
| Llama 3 70B | 密集 | 70B | 0.3x | 180ms |
| Llama 4（估计） | MoE | ~10B | 2.5x | 45ms |
| Qwen2.5-MoE-A2.7B | MoE | 2.7B | 3.0x | 35ms |
| DeepSeek-V3 | MoE | 37B | 2.5x | 60ms |

*注意：吞吐量和延迟为近似值，高度依赖于硬件、批处理大小和工作负载特性。*

## MoE 关键优势

混合专家架构相比传统密集模型具有显著优势，特别是对于大规模部署。以下是 DeepSeek-V3 和 Llama 4 等模型展示的关键优势：

### 1. 稀疏激活

**工作原理：**

MoE 模型仅为每个 token 激活一部分专家，通常为总参数的 5-20%。这种稀疏激活大幅减少了计算需求，同时保持模型容量。

**示例（DeepSeek-V3）：**

```text
总参数：671B
每 Token 活跃参数：37B
激活率：5.5%

与密集模型对比：
- 密集 671B：每 token 671B FLOPs
- DeepSeek-V3：每 token 37B FLOPs
- 减少：94.5% 的 FLOPs
```

**优势：**

- **更低延迟：** 每个 token 计算更少，意味着生成更快
- **更高吞吐量：** 相同硬件每秒处理更多 token
- **能效：** 减少计算意味着更低功耗
- **成本节约：** 相比密集等效模型，服务成本低 40-60%

### 2. 处理更大的参数量

**挑战：**

密集模型线性扩展——将质量翻倍通常需要 4-10 倍的参数，这直接增加了内存、计算和成本。

**MoE 解决方案：**

MoE 架构将总参数量与活跃计算解耦，使得模型可以拥有数千亿甚至数万亿参数，同时保持推理成本可控。

**实际示例：**

| 模型 | 总参数 | 活跃参数 | 内存（FP16） | 推理速度 |
|-------|-------------|---------------|---------------|----------------|
| 密集 GPT-4（估计） | ~1.7T | ~1.7T | ~3.4TB | 基准 |
| DeepSeek-V3 | 671B | 37B | ~1.3TB | 快 3 倍 |
| 质量 | 相当 | 相当 | 少 62% | - |

*注意：内存数据仅代表模型权重。实际推理内存包括 KV 缓存、激活和运行时缓冲区的额外开销。*

**MoE 实现方式：**

1. **专家专业化：** 不同的专家学习互补的技能
2. **选择性激活：** 仅相关专家处理每个 token
3. **高效存储：** 专家可以分布到多个 GPU 上
4. **动态加载：** 按需加载专家以实现内存效率

**优势：**

- **大规模：** 具有 1T+ 参数的模型变得实用
- **内存效率：** 跨分布式内存存储专家
- **灵活部署：** 通过添加更多 GPU 和更多专家来扩展
- **面向未来：** 架构可超越当前硬件限制进行扩展

### 3. 更快的训练速度和更高的准确性

**训练效率：**

MoE 模型相比密集模型，每训练 FLOP 实现更好的质量，从而实现更快的迭代和更低的训练成本。

**训练速度对比：**

| 模型类型 | 达到目标质量的 FLOPs | 训练时间 | 成本 |
|------------|------------------------|---------------|------|
| 密集 | 1.0x（基准） | 100 天 | $10M |
| MoE（相似总参数） | 0.25x | 25 天 | $2.5M |
| MoE（4 倍总参数） | 0.4x | 40 天 | $4M（更好质量） |

**MoE 训练更快的原由：**

1. **稀疏梯度：** 仅激活的专家收到梯度更新
2. **并行学习：** 不同专家同时学习不同技能
3. **高效容量：** 更多参数无需成比例的计算成本
4. **更好的泛化：** 专家专业化提高整体质量

**准确性提升：**

MoE 模型通过专业化实现更高准确性：

```text
基准性能（归一化为 100）：

密集 70B：
├─ 代码：75
├─ 数学：72
├─ 推理：78
└─ 平均：75

MoE（DeepSeek-V3，37B 活跃）：
├─ 代码：88（代码专家）
├─ 数学：85（数学专家）
├─ 推理：90（推理专家）
└─ 平均：88（提升 17%）
```

**MoE 准确性更高的原由：**

- **专业化：** 专家专注于特定领域/技能
- **容量：** 更多总参数捕获更多知识
- **效率：** 每任务更好的参数利用率
- **多样性：** 不同专家提供互补能力

### 综合影响

稀疏激活、更大参数数量和改善的训练相结合产生了倍增效应：

**ROI 示例（DeepSeek-V3 vs. 密集等效模型）：**

```text
使用密集模型达到与 DeepSeek-V3 相似的质量：

所需密集模型：
- 参数：~200B（活跃）
- 训练成本：$15M
- 每 1M tokens 推理成本：$15
- 延迟：200ms TTFT

DeepSeek-V3（MoE）：
- 参数：37B（活跃），671B（总）
- 训练成本：$6M（节省 60%）
- 每 1M tokens 推理成本：$5（节省 67%）
- 延迟：60ms TTFT（快 70%）

面向服务的部署 3 年总拥有成本节约：~$50M
```

### MoE 优势最大化场景

MoE 优势在以下场景中最为显著：

1. **高容量服务：** 每秒数千个请求
2. **多领域应用：** 多样化查询类型受益于专业化
3. **成本敏感型部署：** 优化 $/token 是优先事项
4. **质量要求：** 需要最先进的性能
5. **长期部署：** 初始复杂度随时间得到回报

### 实施考虑因素

为实现这些优势，需考虑：

- **推理引擎：** 使用 MoE 感知引擎（vLLM、SGLang、TensorRT-LLM）
- **硬件：** 用于专家通信的高带宽互连
- **监控：** 跟踪专家利用率和负载均衡
- **优化：** 调整专家并行和缓存策略
